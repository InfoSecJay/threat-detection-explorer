Detection Explorer Teardown

Seventeen findings from walking the live site as a first-time visitor, a search engine, a link unfurler, and an API client. Ordered by what blocks you from sharing it, then by what stops it lasting.

Reviewed 30 Aug 2026 Build v1.4.0 · commit beaec550 Corpus 15,579 rules · 13 repos

The verdict in one paragraph

The hard part is done and done well. The corpus is real, the normalization is honest, the observable extraction is something nobody else has, and the "What we count" table is the most credible methodology statement I've seen on a site like this. What's missing is everything between a good tool exists and other people find it, trust it, and keep coming back. Right now the site is technically unshareable — a link posted anywhere renders as a naked URL, and Google cannot see a single one of your 15,579 rule pages. Fix that layer first; it is the difference between a portfolio piece and a reference.

The second thing to fix is a trust problem you may not have noticed: the hygiene score, as currently normalized, publishes a vendor leaderboard that reads as an insult to two of your sources. See F09.

A

What you already have that's hard to copy

Short, because you said you know. But it's worth naming precisely, because the positioning advice later depends on which of these is actually the moat.

Reproducible counts

Pinned commits, glob patterns, exclusion dirs, 5% drift alerting against the GitHub tree. No other aggregator shows its work like this.

Observable extraction

Parsing rule logic down to processes, event IDs, paths and regexes across ten query languages is the genuinely novel engineering here.

The longitudinal record

Weekly deltas, twelve-week pulses, newly-covered techniques. This is the only asset that compounds and that a competitor starting today cannot have.

Gap framing

Ranking 185 actors and 826 tools by distinctive techniques nobody detects is a better product than search, and it's buried under search.

B

Blocks sharing — fix before you post it anywhere

Every item here is a few hours of work and each one is currently costing you most of the audience you'd get from a single good post.

F01

Zero Open Graph tags on every pageCritical

I checked the DOM on the home page and on a rule detail page: meta[property^="og:"] returns 0 elements. No og:title, no og:description, no og:image, no Twitter card, no canonical. A rule page dropped in a Slack channel, a LinkedIn post, a Discord server or a Teams chat unfurls as a bare blue link. Your entire organic growth path is one detection engineer pasting a rule link somewhere, and that path is currently dead.

Server-render per-page OG tags (you already compute the title and description client-side via useDocumentMeta — the data is right there). Then add a generated OG image endpoint: rule title, source badge, language, ATT&CK technique, hygiene score on your terminal-green card. A shared rule link that unfurls into a good-looking card is the single highest-leverage change on this list.

F02

Nothing is server-rendered, so nothing is indexedCritical

Every route returns the identical Vite shell — I fetched /llms.txt, /sitemap.xml and /api/docs and all three returned the same index.html. Titles and descriptions are injected client-side after hydration. Google can execute JS, but it does so on a deferred second pass and inconsistently at this scale; 15,579 rule pages behind a client-side router will not enter the index in any meaningful way. Someone searching "detect T1003.001" or "Sigma rule certutil download" will never find you.

Prerender the detail routes at build time or put SSR in front (vite-plugin-ssr, or a small prerender worker on Cloudflare). You don't need the whole app rendered — just detection, technique, actor and observable detail pages, which is where the searchable long tail lives.

F03

robots.txt points at a sitemap that doesn't existCritical

/robots.txt declares Sitemap: https://detectionexplorer.io/sitemap.xml. That URL returns the SPA shell, not XML. The real generator is /api/sitemap.xml on the backend — which the same robots.txt blocks with Disallow: /api/. So the sitemap is simultaneously unreachable and disallowed.

Proxy /sitemap.xml to the backend generator at the edge, or write it to static at build. Two lines. Then submit it in Search Console.

F04

No mobile navigationHigh

At 375px the header nav runs off the right edge — HOME, DETECTIONS, MITRE are visible and the remaining five items are simply gone, with no hamburger and no horizontal scroll affordance. The LIMIT select on /detections is also clipped at the viewport edge. Links shared on LinkedIn get opened on phones more often than not.

Collapse to a drawer below 768px. The dense table can stay horizontally scrollable — that's fine and expected — but the navigation can't be.

C

Operational — the things that break when a post lands

These don't hurt today because traffic is low. They are exactly what fails on the day a post does well.

F05

Unauthenticated write endpoints in the public OpenAPI specVerify today

The backend is hardcoded in the bundle and directly reachable at threat-detection-explorer-production.up.railway.app, with full Swagger docs at /docs and a complete spec at /openapi.json. That spec declares no security schemes at all — components.securitySchemes is empty and every operation's security is null, including POST /api/repositories/sync-all, POST /api/repositories/ingest-all, POST /api/mitre/refresh and POST /api/scheduler/trigger. I did not call any of them — triggering a full re-ingest on your production database isn't mine to do. But if there's no middleware enforcing auth outside the spec, anyone reading this spec can make your box clone thirteen repos on demand, repeatedly.

Verify first. Then: put mutating routes behind a bearer token, drop them from the public router entirely and drive syncs from the scheduler or a GitHub Action, and set openapi_url=None/docs_url gated for the admin surface. Keep the read spec public — see F17.

F06

No caching anywhere, single container, slow first paintHigh

Measured on a warm load of /detections: /api/detections/facets 1,503 ms, /api/detections 1,278 ms, /api/detections/filters 695 ms. No Cache-Control header on any API response. No CDN in front of the backend. One Railway container serving every query for every visitor, with the browser talking to it cross-origin directly.

Your corpus changes once a day — that is close to the most cacheable workload there is. Put Cloudflare in front, proxy the API under detectionexplorer.io/api (same origin, kills the CORS preflight too), and set s-maxage=900, stale-while-revalidate=86400 on read routes with a purge on sync completion. Facets and filters should be a static JSON blob regenerated nightly, not a live query.

F07

The visible loading state reads as an empty siteMedium

On /actors, the page paints ACTORS — (0 with rules) and SOFTWARE + TOOLS — (0 with rules) for the ~1.5s the facets call takes. A first-time visitor's first impression of your best page is a catalog with zero coverage. Same pattern on the home page's actor ranking, which shows loading ranking….

Skeleton rows, and bake the top-level counts (185 actors, 826 software, 15,579 rules) into the prerendered HTML so the numbers are correct before any request resolves.

F08

"Open source" with no LICENSE fileMedium

The About page calls it "an open-source tool" and links InfoSecJay/threat-detection-explorer, which is public — but the GitHub API reports no license, which legally means all rights reserved. Nobody can fork, contribute or run it. The repo description also still says five sources, and it has zero stars, which is worth noting only because it tells you the distribution work hasn't started.

Add a license (Apache-2.0 or AGPL depending on whether you'd mind a vendor reskinning it), refresh the description, add a real README with a screenshot, and pin it on your profile.

D

Trust — what a skeptical detection engineer will push back on

This is the section that matters most for "long lasting". Credibility with maintainers and with your peers is the thing that's slow to build and fast to lose.

F09

The hygiene score is a schema-similarity leaderboard, and it insults two of your sourcesReputational

I sampled 50 recent rules per source and averaged the score. The spread isn't measuring hygiene — it's measuring how closely each repo's metadata resembles Sigma/Elastic conventions:

Sublime34

Sublime's email rules are some of the best-written detection content in your whole corpus — the one I opened had a five-paragraph description of a real phishing TTP with Unicode evasion detail. It scored 33/100: MITRE ATT&CK 0/20 because MQL email rules don't carry technique tags, and Testability 0/20 because the repo's test convention isn't the one you check for. You've built a page that tells a Sublime or Chronicle maintainer their work is failing. That is not the first impression you want when you eventually want those maintainers to link to you.

Three changes. Normalize per format — score each rule against what its language and repo conventions can actually express, so an MQL rule isn't docked for a field that doesn't exist in MQL. Rename it: Metadata Completeness, not Hygiene, and never surface a cross-vendor ranking of it. And keep the "rule hygiene, not detection accuracy" caveat, but move it above the number instead of below.

F10

Permalinks use an internal UUID that isn't the upstream rule IDHigh

The rule I opened lives at /detections/37c8593b-9f9e-d0d4-262a-c8f0238b830d while its displayed Rule ID is c28c8fa1-5378-552f-9a0f-c6d186a406dc, and the upstream ID doesn't resolve. If that internal ID is a database surrogate, or derived from file path or row order, then every shared link, every bookmark, every export and every citation breaks on the next re-ingest. For a site whose value is being linkable, permalink stability is a load-bearing property.

Make the ID a deterministic function of (source, upstream_id) — a UUIDv5 over that pair — so it survives re-ingest, path moves and full rebuilds. Then publish that guarantee on the methodology page, and accept the upstream ID as an alias route so people can link with the ID the vendor uses.

F11

404 on rules that were removed upstreamMedium

Your own 404 copy admits this: "the rule may have been removed upstream." You already know links rot. A dead link on a site people are meant to cite is worse than a stale page.

Serve tombstones, not 404s. "This rule was tracked from 2025-11-02 until 2026-08-12, when it was removed from SigmaHQ at commit abc123. Here's the last version we saw, and three current rules covering the same technique." That page is more useful than the live rule was, and it's a thing only you can produce — nobody else kept the record.

F12

"Same behaviour, other vendors" returned zero other vendorsMedium

Cross-vendor comparison is your headline claim. On the Sublime rule I opened, that panel read "12 rules · 0 other sources" and filled all twelve slots with other Sublime rules matched on source table type.inbound — i.e. "also an inbound email rule." That's not similarity, it's a fallback that hides the fact that there was no match.

When there's no genuine cross-vendor match, say so — "no equivalent found in the other 12 sources" is a finding, and it's the gap-analysis story you're already telling elsewhere. Keep same-source neighbours in a visually separate, clearly labelled block.

F13

Search relevance ranking is unweightedMedium

Specific queries are good — "powershell encoded command" returns the right rule first, "okta mfa bypass" and "Salt Typhoon" both land well. Broad ones fall apart: q=ransomware returns 588 hits whose top three are "Potential NFS Destructive Operation Burst", "Linux EFI Bootloader File Deletion" and "Speculus - Network traffic to or from high-risk IP indicator" — not one with the word in its title. First-time visitors type broad words.

Boost title and rule-name matches heavily over description and query-body matches (Postgres setweight A/B/C/D if you're on tsvector). Broad-query relevance is what a first-time visitor judges the whole site on.

F14

Per-source licenses aren't shown where they matterMedium

The legal notice correctly tells people to check each repo's license, which puts the work on the reader at exactly the moment they're about to copy a query into production. The licenses genuinely differ and some of them matter — Elastic's rules are ELv2 with a managed-service restriction, and the person copying from your site is very often at an MSSP.

A license badge in the source table on /about, and one on every rule detail page next to the source badge, linking to the upstream LICENSE. It costs you a column and buys you a lot of goodwill with the vendors.

E

Structure and reach

F15

Your most credible page is buried and its obvious URL 404sHigh

The "What we count" table — pinned commits, glob patterns, exclusion dirs, per-source scope prose, drift alerting — is the single strongest trust artifact on the site. It sits at the bottom of /about, below a personal bio, with no nav entry. Meanwhile /methodology returns 404, even though there's already an /api/methodology endpoint. And the same sync story is told in three places: /about, /integrations and /intel, with /integrations adding nothing /intel doesn't.

Promote it to /methodology, put it in the nav, and link to it from every count on the site — the hero's "15,579", the source cards, the coverage percentages. Fold /integrations into /intel. Keep /about for the bio.

F16

The digest is your retention engine and it has no subscribe and no permalinkHigh

The weekly digest is the best thing on the site for coming back — themes clustered by technique, per-source deltas, copy-as-markdown. But the only subscription channel is RSS, which most SOC people don't run, and the page is a rolling window: a link you share today shows different content next week, so it can't be cited or archived.

Give every week a URL (/digest/2026-w35) and keep the archive forever. Add email — Buttondown or Listmonk, a few hundred subscribers is a real audience in this niche. Add a Slack/Teams webhook format, since that's where detection teams actually read things. Then post the same digest to LinkedIn every Monday for six months; that consistency is what turns it into a fixture.

F17

Your most durable asset is the API, and it's invisibleStrategic

There's a complete, well-shaped 64-endpoint API with a full OpenAPI 3.1 spec and Swagger UI — reachable only if you know to guess the Railway hostname. Nothing on detectionexplorer.io links to it. No version prefix, no rate limits, no fair-use terms, no examples. Also missing: a contribution path. No "suggest a source", no issue link, no discussion, nothing that lets a stranger participate. Projects that last have a way in.

Publish it at detectionexplorer.io/api/docs with a /v1 prefix and a stated deprecation policy, add rate limits and a short fair-use note, and write three worked examples (pull today's new rules into a Slack channel; export a Navigator layer for an actor; diff your own rule set against the corpus). People who build against your API stop being visitors. Pair it with the MCP server you've been planning — that's the version of this that gets used inside an agent loop daily.

F

What makes this last

The findings above are execution. This part is the bet, and it's the one worth arguing with me about.

The problem

"Search 15,579 detection rules" is a commodity in 2026. Sigma has a search. Elastic has docs. An LLM answers "give me a rule for T1003.001" instantly and will keep getting better at it. If browsing is the pitch, the site's value decays as models improve. Nothing on the home page currently says why a person should use you rather than ask a model.

The asset

The longitudinal record is the only thing that compounds. Observable extraction is clever but reproducible by a well-resourced team in a quarter. The normalized schema is a moat measured in months. But "what did the open detection ecosystem cover on 2026-08-30, and how did that change over three years" cannot be built by someone starting tomorrow — it requires having been running since today. Keep every nightly snapshot forever, even the ones you don't currently surface.

The pitch

Lead with the gap, not the catalog. "89.9% of ATT&CK techniques have at least one public rule — here are the 21 that have none, and the 40 actors whose distinctive TTPs nobody detects" is a headline people repost. "15,579 rules, searchable" is a headline people scroll past. Your /actors gap ranking is already the most interesting page on the site; it should be the front door, with search as the utility underneath it.

The proof

Get cited, not just visited. Traffic decays; citations compound. Publish one quarterly coverage report with a stable URL and real numbers — coverage growth by technique, which vendors moved, what went uncovered — and make the underlying data downloadable. Conference talks, vendor blogs and threat reports will link to it, and inbound links are the only SEO that survives a platform change. This is also the thing that makes the site outlive your interest in maintaining it.

The tension

"Engineered by Jay Tymchuk" cuts both ways. It's excellent for the portfolio use — and this is clearly a strong portfolio piece — but a site presented as one person's project has a visible bus factor, and enterprise readers discount it accordingly. If longevity is the real goal, shift the framing toward a project with contributors, a license, and a governance note, and keep the byline in a credits line. If the portfolio is the real goal, ignore this one; the two goals genuinely conflict and it's worth deciding which you're optimizing for.

Smaller things worth a line
  • Name inconsistency: the site calls itself Threat Detection Explorer, the domain and your resume say Detection Explorer. Pick one — it's the difference between people finding you again and half-remembering.
  • Google Fonts loads three families (Orbitron, Rajdhani, JetBrains Mono) as a render-blocking stylesheet from a third-party origin. Self-host and subset; it's ~18KB and a DNS round trip on first paint.
  • The default sort on /detections is Created (Newest), which shows a first-time visitor eight Sublime email rules in a row. Relevance or a curated "start here" set would sell the corpus better.
  • The query language is genuinely good (actor:"Salt Typhoon", tech:T1003.001 platform:windows) and the example chips are the right call — but /query isn't in the nav, and the syntax help is a ? button most people won't press.
  • Rule detail pages show Author: unknown where upstream metadata is missing. Falling back to the repo name would read better than "unknown" and is more accurate.
  • No analytics that I could detect. You'll want to know which rule pages get shared before deciding what to build next — Plausible or Umami, self-hosted, no cookie banner needed.
